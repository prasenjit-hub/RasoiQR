# AGENTS.md

Multi-tenant restaurant ordering SaaS. React 19 + Vite 7 + TypeScript 5 + Supabase. Indian market (₹, 5% GST, Inter font).

## Quick commands

```bash
npm install
npm run dev              # vite dev server on port 3000
npm run build            # tsc -b && vite build
npx tsc -b --noEmit      # typecheck only
node database/scripts/smoke-test.mjs   # anon-access smoke test (4/4 expected)
node database/scripts/check-migrations.mjs  # migration record drift check (files / ledger / this file)
```

## Auth architecture (Phase 2.7 — @supabase/ssr)

Uses `@supabase/ssr` `createBrowserClient` (not `@supabase/supabase-js` `createClient`). Sessions stored in **cookies** (document.cookie) instead of localStorage. This bypasses two P0 bugs in @supabase/supabase-js v2.86:
- Web Locks API deadlock in getSession/getUser (#2111)
- Async callback deadlock in onAuthStateChange

### Key files

- `src/config/supabase.ts` — `createBrowserClient` singleton, cookie-based storage, PKCE flow
- `src/contexts/AuthContext.tsx` — single AuthProvider for admin + restaurant slots
  - 8s outer timeout (safe default, never blocks UI)
  - `profileFetchInFlight` dedup (faster than concurrent RPC calls)
  - `mountedRef` + `safeSetState` (React 19 StrictMode safety)
  - `setTimeout(0)` in `onAuthStateChange` callback (Supabase canonical pattern)
  - Defensive PostgREST response normalization (handles both `RETURNS TABLE` array and `RETURNS SETOF`/single-object)

### Auth flow

1. Page loads → `getSession()` reads cookies (instant, no network)
2. `getUser()` validates JWT with server (authoritative)
3. `loadProfile()` calls `get_my_admin_profile` / `get_my_restaurant_profile` RPCs
4. If both RPCs return empty → user sees NotAuthorized page (cookies preserved, no signOut)
5. If one RPC errors (transient) → user stays signed in, no profile loaded

### Why NOT `@supabase/supabase-js` directly?

Supabase JS v2.86 has two unresolved P0 bugs that can deadlock the SDK. Using `@supabase/ssr` with cookies is the recommended production path per Supabase.

## Database schema & migrations

- 10 tables: `registration_requests`, `restaurants`, `users`, `menu_categories`, `menu_items`, `orders`, `admin_users`, `notifications`, `waiter_calls`, `restaurant_tables`
- All have RLS enabled. Direct client queries against `admin_users` and `users` are blocked by RLS.
- **Never** let the client query `admin_users` / `users` directly. Use the SECURITY DEFINER RPCs.

### Run-from-scratch

**There is no run-from-scratch file. The migrations *are* the from-scratch path.** `database/migrations/000 … 049` applied in order is the only supported way to build the schema; the live database was built that way. Every database change needs **three records**, and all three are written by hand — which is exactly why they drift: (1) a numbered file in `database/migrations/`, (2) a `supabase_migrations.schema_migrations` row in the live database, (3) a row in the migration table below. A migration file must end with its own ledger `INSERT` (032 and 033 show the pattern) — 033 originally shipped without one, so the live database never recorded it and nothing flagged the gap; that row is now present and 033 carries its own `INSERT ... ON CONFLICT DO NOTHING`. `node database/scripts/check-migrations.mjs` verifies (1) and (3) offline and prints the query for (2); run it before calling any database change done.

⛔ **`setup.sql` is RETIRED — do not run it, and do not "fix" it.** It was reconciled through **032 only**, so running it on an empty database builds a 2026-10 schema that re-opens every hole 033–049 closed (writable `orders` and `restaurants`, missing `waiter_calls` / `restaurant_tables` / `get_menu_version` / the slug CHECK, plus the blanket `GRANT … ON ALL TABLES … TO authenticated`). It is now **defused rather than deleted**: a `DO $retired$ … RAISE EXCEPTION` guard sits at the top, and the entire original 1,400-line body is wrapped in a block comment, so even a runner that ignores errors (`psql` without `ON_ERROR_STOP`) finds nothing executable after the guard. The history stays readable, and no tool can build the old schema by accident.

  - **To bring it back you must do all three:** reconcile 033–049 into the body, remove the guard *and* the surrounding block comment, and **test it on an empty project** — never on production. Until someone actually does that, `database/migrations/` is the truth and this file is reference material for the 2026-10-09 state of the database.
  - The drift check still reports it as *behind* (`WARN E … does not build 033 … 049`). **That warning is expected and is not a problem** — the script parses raw text and cannot know the file is retired; leaving it visible is the point, since it is the only machine-readable signal that the two paths disagree.
  - Direct consequences: [`database/README.md`](database/README.md) and [`LAUNCH_PLAN.md`](LAUNCH_PLAN.md) still tell you to run `setup.sql`; where they conflict with this section, this section wins. The admin-bootstrap script (`create-admin.mjs`) only needs the tables to exist — it does not care which path built them.

| 039 | Order idempotency — a submit that succeeded on the server but failed on the wire can no longer create a second order. `orders.client_ref` (nullable uuid) holds a client-generated reference with a **partial** unique index `orders_client_ref_key ON (restaurant_id, client_ref) WHERE client_ref IS NOT NULL`, so NULL-reference rows (admin/phone/old clients) stay unconstrained. `customer_create_order` gained `p_client_ref uuid DEFAULT NULL`: step 0 replays an existing `(restaurant_id, client_ref, customer_phone)` row as-is (no second order, no re-validation, no `sales_count` bump), and the INSERT carries `ON CONFLICT (restaurant_id, client_ref) WHERE client_ref IS NOT NULL DO NOTHING` so a simultaneous race hands back the winner's row instead of failing. | 040 | Order rate limits — 039 made a *repeat* submit idempotent but nothing capped **new** orders, so an anon script could put hundreds of real orders in front of a kitchen (each bumping `menu_items.sales_count`). `customer_create_order` now runs three caps **after** the 039 replay and **before** any price work: **phone** ≤ 5 orders / 60 min, **table** ≤ 8 orders / 60 min (dine-in only, `(restaurant_id, table_number)`), and a **burst brake** ≤ 20 orders / 5 min per restaurant — the only one that also catches an attacker varying both table and phone, and it is a burst window, not a throughput cap (a real rush recovers in 5 minutes). `cancelled`/`rejected` orders never count, so a mistake or a staff cancellation does not spend a guest's quota. Limits are `CONSTANT`s at the top of the body (`c_phone_max_per_hour`, `c_table_max_per_hour`, `c_burst_max_per_5min`) — tune those three, nothing else. Signature is unchanged (same 8 args), so this is a plain `CREATE OR REPLACE`: no overload, grants inherited. New indexes `orders_phone_created_idx (customer_phone, created_at DESC)` and `orders_restaurant_table_created_idx (restaurant_id, table_number, created_at DESC)`; the 5-minute burst rides the existing `(restaurant_id, created_at DESC)` index. | 041 | Rate-limit retune (research-backed) + real 429 — 040 chose its numbers by judgement; reviewed against published practice, **PHONE 5/h was tighter than the professional starting range** for anonymous create/checkout flows (Cloudflare's own examples: 10/10min then 20/h per caller) and a phone is a person who may legitimately order at a second restaurant, so it is now **10/hour** (still catches a script on one number, without refusing a real guest). **TABLE stays 8/hour** — multi-round ordering is a supported normal workflow (Toast/Shift4) and the planning envelope is ~1–3 submissions per sitting, so 8 is ~3× a realistic table. **BURST 20 → 30 per 5 min** (4/min → 6/min): still stops a flood while a large fast-casual peak no longer risks tripping it; it remains a burst window, not a throughput cap. The burst refusal now raises **SQLSTATE `PT429`** (PostgREST maps `PT…` to that HTTP status) because it is the one transient refusal, while phone/table stay plain business errors on purpose — retrying them seconds later cannot help, which is exactly what the client copy says (“ask a member of staff” vs “try again in a few minutes”). Deliberately **not** done: a hard per-restaurant hourly cap (no defensible universal number; depends on the venue's real kitchen capacity) and counting retries against the quota (would punish guests whose response was lost — the 039 case). ⚠️ Refusals cannot be logged inside the RPC: PostgREST runs the call in one transaction and the raised error aborts it, so a denial row would be rolled back — the API logs are where refusals are visible. Signature unchanged, so plain `CREATE OR REPLACE`. |
| 042 | Order burst becomes **alert-only** — 041's burst brake (30 orders / 5 min per restaurant) was refusing **real guests**: 30/5min = 360/hour is **not** above published high-throughput QSR peaks (Chipotle's fastest units: >350 transactions in a lunch hour ≈ **29.2 per 5 min**; one Chick-fil-A outlet: 326 drive-thru cars/hour ≈ 91% of 360), a rolling 5-minute count reads a rush's **shape** rather than its volume (a 100–150 orders/hour venue can put 30+ into one interval), and — worst — it was the **only** whole-restaurant cap, so 30 cheap orders were enough to keep *every* genuine guest refused (a denial-of-service lever). `customer_create_order` still computes the count, but crossing `c_burst_alert_per_5min` (30) now only raises a `WARNING` and writes **one deduplicated `notifications` row** (`type = 'order_burst'`, dedupe `c_burst_alert_dedupe_minutes` = 5) — **the guest's order is never refused**. The `RAISE SQLSTATE 'PT429'` refusal and its client copy are gone (the two remaining `customerOrderErrorMessage` branches are the per-identity ones). Phone (10/h) and table (8/h) both still refuse at this point (the table half was later removed by 043) — but ⚠️ **only the phone cap is genuinely self-harming**: `table_number` is a *shared* identity for every guest at that table **and is client-supplied** (`?table=N` on the table QR, or typed by the guest on the Master QR), so a table cap can refuse real guests and can be used to lock a real table. See the gotcha below. ⚠️ Deliberate pilot-phase trade-off: a script varying **both** phone and table is no longer stopped at all — the alert is a tripwire for a human, and the replacement is L2 (Turnstile / proof-of-work) in [docs/plans/2026-10-16-order-abuse-defense-plan.md](docs/plans/2026-10-16-order-abuse-defense-plan.md). The alert insert is wrapped in its own `EXCEPTION` block on purpose (telemetry must never break a guest's order) and reports its own failure as a WARNING rather than swallowing it. Signature unchanged (same 8 args) → plain `CREATE OR REPLACE`. Adds `notifications_restaurant_type_created_idx` on `(restaurant_id, type, created_at DESC)` — `notifications` is this migration's first writer. |
| 043 | The per-table order cap is **removed** — 040's table cap (8 orders / hour per `(restaurant_id, table_number)`) failed the same test 042 applied to the burst: `table_number` is **shared by every guest at that table and is client-supplied** (the table QR carries only `?table=N`; on the Master QR the guest types it into the `Your Table Number` field of [CheckoutContent.tsx](src/pages/customer/components/CheckoutContent.tsx)), so 8 cheap orders could lock a **real** table for an hour and the attacker just moves to the next number — the same denial-of-service lever as the burst, one level down. It also refused real guests: each device keeps its own cart and no login is involved, so a 12-guest party ordering on separate phones over two rounds (24 submissions) hit the 9th. And it barely stopped a script, which varies the table anyway — low protection, real cost. `customer_create_order` loses the table count, its refusal, `c_table_max_per_hour` and `v_recent_table`; `orders_restaurant_table_created_idx` is **dropped** (it existed only for that window — nothing else filters `orders` by table + time: `get_orders_for_tracking` merely *returns* the column and filters by `o.id = ANY(p_order_ids)`, and no client query filters by `table_number` at all, only displays it). ⚠️ **After this the public order path has exactly ONE refusal: the phone cap (10/hour)** — the only identity that belongs to the caller. Everything else is an alert (042) or a validation error, so a script varying phone and table is no longer stopped at the database level at all; that is exactly why L2 (invisible bot friction) is the next real work, not an enhancement. Signature unchanged (same 8 args) → plain `CREATE OR REPLACE`. The client copy for the removed message is deleted from `customerOrderErrorMessage` in the same change. |
| 044 | Owner-declared tables — `restaurants.table_count` (nullable `INT`, `CHECK 1..200`) is the owner saying how many tables the venue has, and `customer_create_order` now refuses a dine-in table outside it. The gap: nothing in the database knew a table existed — the QR generator looped `1..tableCount` on a number the owner typed and never stored ([qrPdfService.ts:130](src/services/qrPdfService.ts#L130)) — so `orders.table_number` accepted `'999'`, `'abc'`, `''`. Named tables are not supported: the bound is numeric because the QR generator only emits `1..N`. Client: the profile form gained a validated `Number of tables` field, [QRCodeManager.tsx](src/pages/restaurant/components/QRCodeManager.tsx) generates table QRs from `table_count` (and shows an info note instead of offering QRs for tables the server would refuse when it is NULL), and the refusal has its own `customerOrderErrorMessage` branch. |
| 045 | Tables become real rows and a QR carries a **code**, not a number — 044's range check made a table a *validated string*; this makes it an **entity**. `restaurant_tables` (label, `sort_order`, random 12-hex-char `code`, `is_active`, `rotated_at`) is one row per table, and `update_my_restaurant(p_table_count)` stays the single write path but now **syncs** rows through `sync_restaurant_tables`: 1..N created (each with its own code), numeric labels above N deactivated — **not deleted**, so raising the count back revives the *same* code and an already-printed standee starts working again. QR URLs are now `/menu/<slug>?t=<code>`; `resolve_table_code(slug, code)` (anon) is the one way to read it back into a label, and `customer_create_order`/`customer_call_waiter` take the code, resolve the label **from the database** and ignore anything the client calls a table. ⚠️ **Dine-in is code-only from here (a deliberate fail-CLOSED change)**: the product decision is **Master QR = Takeaway**, so a restaurant with no declared tables takes takeaway only, and 044's range check went away with the typed path it guarded (resolving a per-table code is strictly stronger — it proves *which* table). `p_table_number` stays in the order signature but is **never read**, so a stale deployed tab gets the clear "scan your table's QR" refusal instead of PostgREST's "function not found". ⚠️ The registry has **no client privilege at all** (explicit `REVOKE`, because `ALTER DEFAULT PRIVILEGES` hands every new table to `anon`/`authenticated`), reads go through `get_my_tables()`, and `guard_restaurant_tables` raises `42501` on a client write — verified live with a temporary grant *and* an UPDATE policy in place, so the trigger is genuinely the layer that survives a returning blanket grant. Owner actions `owner_rotate_table_code` / `owner_set_table_active` rotate or stop **one** table: that is the operation a shared HMAC secret cannot express, and the reason a random code was chosen over a signed token. ⚠️ Both DROP+CREATE paths (`customer_create_order` 9 args, `customer_call_waiter` renamed param) lose their ACL, so the migration re-issues grants and the verify block asserts anon cannot execute any owner-only/internal function. ⚠️ **The code is still a bearer token** — a photo of the standee can be shared, so this ends invention/enumeration/garbage numbers and makes a leak revocable per table, not "is the guest really sitting there". | 046 | Guest menu refresh becomes a **version check** — the customer menu kept itself fresh by re-asking `get_menu_for_restaurant` every 60 s, which is correct but asks the wrong question ("what is the menu?" instead of "did anything change?"), so the whole menu came back and was thrown away; measured with `row_to_json` at **659 bytes/item** (~4 KB today at 6 items, ~33 KB at 50, ~99 KB at 150), ten times per visit — the one cost in the customer flow that grows with the restaurant instead of staying flat. `get_menu_version(p_restaurant_id)` (SECURITY DEFINER, `STABLE`, pinned `search_path`, anon-callable, `PUBLIC` revoked) returns `count(*) \| md5(every visible row's id + updated_at)` over exactly the rows a guest could order (`is_available = TRUE`, the same filter `get_menu_for_restaurant` applies) — **35 bytes** measured live against a 4 KB menu. - `customer_create_order` — anon-callable, SECURITY DEFINER: server-side pricing, per-line quantity 1–50, 50-line cap, expired-trial guard (026, respecting the 029 access window) and a **code-verified table** (045: dine-in requires a `p_table_code` that resolves to an active table of that restaurant; the label is read from the database, `p_table_number` is ignored)
- `get_orders_for_tracking` / `get_order_status` — anon-callable customer tracking RPCs (023)
- `customer_call_waiter(slug, table_code)` — anon-callable, SECURITY DEFINER: the customer "Call Waiter" button (036, now code-verified by 045). Same active + expired-trial guards as `customer_create_order`, and it **dedupes**: an open call for that table is returned with `already_pending = true` instead of stacking a second one. Caps at 6 calls per table per hour — the cap survived 043's objection because the table is no longer caller-chosen.
- `customer_get_waiter_call(id)` — anon-callable, returns only `id` + `status` for one call, so the menu can poll. The unguessable uuid is the capability.
- `acknowledge_waiter_call(id, status)` — owner-only: claims (`acknowledged`) or closes (`resolved` / `cancelled`) a call. Ownership comes from the id + `get_my_restaurant_id()`, and a resolved call can never be walked backwards.
- `admin_create_restaurant` — authenticated-only, `PERFORM assert_admin()` guard. Since 047 it also **decides the slug itself** (normalise → `r-<hex>` fallback → `-2`/`-3` auto-suffix on collision), so the value the browser sends is a suggestion. It returns the old `TABLE(restaurant_id, user_id, success, message)` — read the final slug back with `select slug from restaurants where email = …`.
- `update_my_restaurant` — authenticated-only, SECURITY DEFINER: the owner's profile/branding write path (name, owner, phone, email, city, address, type, logo, banner) plus `table_count` (044), which it also turns into table rows (045). Validates server-side and never touches `slug`, `qr_code_url`, subscription or account state.
- `get_my_tables()` / `owner_rotate_table_code(id)` / `owner_set_table_active(id, boolean)` — owner-only (045): the table list with its codes, and the two per-table actions. `restaurant_tables` has no client grant, so these are the only way in.

### Public order gate — Turnstile + the `submit-order` edge function

**Why it exists.** The public order path is the only unauthenticated *write* in the product, and every database-side brake that used to slow a script down was removed on purpose: 042 made the restaurant-wide burst alert-only, 043 dropped the per-table cap. That leaves exactly **one** refusal — the 10/hour phone cap — and a script simply uses a different number. So before this, **nothing** stopped a script that varied both phone and table. Turnstile is that something: it raises the *cost* of each order rather than proving anyone's identity. Real guests normally see nothing.

**The shape.** `supabase/functions/submit-order` verifies the token with Cloudflare, then calls **the same `customer_create_order` RPC with the same anon client**. It is a gate, not a replacement: server-side pricing, the trial/blocked guards, the resolved table code, the phone cap, item validation and 039 idempotency all run untouched. If you ever find yourself re-implementing a rule inside the function, stop — that is how a second, weaker copy of the order path gets born. **No database change is involved**, which is why Turnstile has no migration number.

**Three outcomes, and each one chosen deliberately:**

| Situation | Behaviour | Why |
|---|---|---|
| `TURNSTILE_SECRET_KEY` missing | **503, fail closed** | A misconfigured deploy must be loud. Falling back to "accept everything" silently switches bot protection off. |
| Cloudflare unreachable / timeout / 5xx | **fail OPEN**, `console.warn` | A verification *outage* is not evidence of a bot. Taking the whole product down to defend against a hypothetical is the worse trade. An attacker cannot make our egress fail; Cloudflare can. |
| Cloudflare answered `success: false` | **403, fail closed** | A definite negative about this specific token — the only case that must refuse a guest. |

**It is OFF by default.** `VITE_TURNSTILE_SITE_KEY` empty → `isTurnstileEnabled` is false → the widget renders nothing and `createOrderAsCustomer` calls the RPC directly, byte-for-byte as before. Setting that variable is a **go-live switch**.

**Rollout — the order matters, and step 4 is not optional:**

1. Create a Turnstile widget in the Cloudflare dashboard (free: unlimited challenges). You get a **site key** (public) and a **secret key** (private).
2. Deploy the function: `supabase functions deploy submit-order`.
3. `supabase secrets set TURNSTILE_SECRET_KEY=<secret>` — then set `VITE_TURNSTILE_SITE_KEY=<site key>` in Vercel (and `.env` locally) and redeploy the frontend.
4. ⚠️ **Close the bypass — but only once the function holds the service-role key.** Until this step an attacker can still call `customer_create_order` directly with the public anon key and skip the gate entirely — the gate would be theatre. ⚠️ The revoke takes away the **function's own** permission too, because a function calling with `SUPABASE_ANON_KEY` runs as `anon`; that is why `submit-order` reads `SUPABASE_SERVICE_ROLE_KEY` (injected into every function by the platform, server-only) and returns **503** when it is missing, and why this step is ordered after the redeploy. Verify one token-bearing call still reaches the RPC *before* revoking, or every order fails with *permission denied for function*. Then:
   ```sql
   revoke execute on function public.customer_create_order(uuid, text, text, text, text, text, jsonb, uuid, text) from anon;
   ```
   `PUBLIC` holds no EXECUTE on it (039 revoked that), so this is a real change and not a no-op. Undo with `grant execute … to anon`. Confirm the exact signature first (`pg_get_function_identity_arguments`), then re-run `npm run verify:submit-order` and place one real order.
   **Deliberately NOT a numbered migration:** it is a lockout that has to land *after* a deploy outside the migration system. As a migration file it would be applied by anyone doing a from-scratch build — or by the next person running pending migrations — before the function exists, which is precisely when ordering breaks. It is a documented operational step, not schema.

**Never put the secret in the browser.** The bundle is public; a leaked secret lets anyone post a `success: true` shaped reply and the whole scheme becomes decorative. Only `TURNSTILE_SITE_KEY` (public by design) is client-side.

**Testing.** `npm run verify:submit-order` runs **the real function source** under Node (same shim trick as `verify-cloudinary-sign`) for **17 cases**. Three of them call the live `challenges.cloudflare.com/siteverify` endpoint with Cloudflare's own documented test secrets (`1x…AA` always passes, `2x…AA` always fails, `3x…AA` reports `timeout-or-duplicate`), so the verification request is genuinely exercised — only the RPC behind the gate is stubbed. It also asserts that an **allow-list**, never the raw browser body, reaches the RPC.

**Client side.** `src/services/turnstile.ts` (lazy script loader, `render=explicit`), `src/pages/customer/components/TurnstileWidget.tsx` (`appearance: 'interaction-only'` — the box only appears if Cloudflare actually needs a human), and a `turnstileNonce` in `CheckoutContent` that remounts the widget. ⚠️ That nonce is load-bearing: a token is **single-use** and lives 300 s, so the previous attempt always spends the current one. It is bumped on every sheet open *and* on every failed submit; without it, "Order More" after a successful order would submit a dead token and read the refusal as a failure.

**Operating it — read this before touching the gate.** [docs/runbooks/order-flow.md](docs/runbooks/order-flow.md) holds the health checks (`node scripts/check-order-gate.mjs`), the **order-sensitive rollback** (the SQL `grant execute … to anon` comes *before* removing the Vercel site key, otherwise guests get *permission denied*), secret rotation, the function redeploy, CSP rules and the Free-plan backup job. Two scheduled workflows back it: `order-gate-health.yml` probes the gate hourly (and keeps the Free project from pausing after 7 idle days) and `db-backup.yml` exports every table plus auth users daily as a 90-day artifact — the Free plan has no server-side backups, so that artifact is the only copy.

## Other gotchas

- **Vite port is 3000** (hardcoded in `vite.config.ts` with `host: "0.0.0.0"`)
- **CI exists now; the deploy gate is two-phase and half-on.** `.github/workflows/ci.yml` runs typecheck + `verify:csp` (the CSP guard — a static read of `vercel.json`, because no compiler can see an HTTP header) + the 17-case `verify:submit-order` suite + build on every push and PR (Node **24**, not 20 — that suite imports the real `index.ts` and Node 20 cannot strip types). **The gate is CLOSED since 2026-10-30:** `vercel.json` sets `git.deploymentEnabled: { "main": false }`, so a push to `main` no longer deploys by itself and the last workflow step (a **Vercel Deploy Hook**) is the only path to production. Only `main` is off, so PR previews still work; never add `github.enabled` — *that* one does disable Deploy Hooks. ⚠️ Do **not** use Vercel's "Ignored Build Step" for this — it runs before CI finishes, its exit codes are inverted, and it also cancels Deploy Hook builds. The ordered procedure and its rollback are in [docs/runbooks/order-flow.md](docs/runbooks/order-flow.md).
- **`VITE_DEMO_MODE` env var** gates demo mode in login + service. MUST be "false" in production.
- **`Promise.allSettled`** used in `getRestaurantStats` so one failing query doesn't kill all stats
- **Self-hosted Inter font** via `@fontsource/inter` (4 weights), not Google Fonts `<link>`
- **`lock: async (_, _, fn) => fn()`** no longer needed (removed in Phase 2.7 — @supabase/ssr uses cookies, not localStorage + Web Locks)
- **Pre-existing lint warnings** (`any` types, `set-state-in-effect`) are unaddressed — don't bother fixing unless editing those files
- **`restaurants` granted columns are deliberately narrow (migration 028).** `authenticated` has table-level `SELECT` and column-level `UPDATE` on profile fields only (`name`, `owner_name`, `phone`, `email`, `city`, `address`, `logo_url`, `restaurant_type`, `qr_code_url`, `slug`). Subscription state is admin-RPC-only. The blanket `GRANT … ON ALL TABLES IN SCHEMA public TO authenticated` in `setup.sql` section 2 is what created the hole — if you ever re-add a blanket grant, you must re-run the `setup.sql` section 2b/2c blocks (or migrations 028 + 030) afterwards, or owners can self-assign a plan and clients regain write access to `users` / `admin_users` / `notifications`. Note that a table-level `REVOKE` does **not** clear column-level grants, so both must be revoked.
- **`free_trial` rows must always have `trial_ends_at` (migration 030).** A `CHECK (subscription_plan <> 'free_trial' OR trial_ends_at IS NOT NULL)` constraint enforces it, because all three expiry checks (trigger, hourly job, order guard) require a non-NULL date before they act — a date-less trial would never expire. A writer that forgets the date now gets a loud constraint error instead of unlimited free service. `admin_create_restaurant` and `admin_update_subscription` both always set one.
- **Trial dates are admin-picked and capped at 60 days.** `admin_update_subscription` takes `p_trial_ends_at` (NULL keeps a still-running date, otherwise restarts at 14 days; anything past `now() + 60 days` raises). The admin plan modal sends it from a `Trial ends on` date input. If you touch that input, note a picked day resolves to **23:59:59 local**, so its `max` must be the last day that still fits under the ceiling (`latestTrialDateInput()` in `AllRestaurants.tsx`) — plain `today + 60` offers a day the client guard and the RPC both reject.
- **RPC-only tables (migrations 030 + 033 + 034 + 036 + 045).** `users`, `admin_users`, `notifications` and `waiter_calls` have **no** client write privileges; `orders` keeps **SELECT only** (033), `restaurants` **SELECT only** (034) and `waiter_calls` **SELECT only** (036, RLS-scoped to the owner's own rows). `restaurant_tables` (045) goes further: **no client privilege at all**, not even SELECT — the owner reads through `get_my_tables()` and a guest through `resolve_table_code()`, so table codes cannot be enumerated by crawling. Client code must go through the SECURITY DEFINER RPCs. `restaurantService.createOrder` (a direct `orders` INSERT) is dead code — do not revive it, the customer path is `customer_create_order`.
- **⚠️ `ALTER DEFAULT PRIVILEGES` auto-grants every privilege to `anon` and `authenticated` on each new table.** Discovered while building 036: creating a table is enough to make it world-writable — it never appears in a diff and no migration wrote it. Every new table therefore needs an explicit `REVOKE ALL … FROM anon, authenticated` and then the narrow grants it actually wants. Verify with `has_table_privilege('anon','public.<table>','INSERT')` after any DDL, not by reading the migration.
- **PL/pgSQL `RETURNS TABLE` names become variables — qualify your columns.** `customer_call_waiter` returns `id`/`status`/`created_at`, and the first live call died with `42702 column reference "status" is ambiguous` because an internal query used the bare column name. Every column reference inside such a function is alias-qualified (`wc.status`, `wc.created_at`); keep it that way rather than relying on `#variable_conflict`.
- **Admin block vs trial expiry (migration 029).** Expiry is suspended for a row only while `access_until > now()`. `enforce_trial_expiry()`, the hourly `expire-free-trials-daily` job and the `customer_create_order` guard all use that same rule, so they cannot disagree. Reopening an already-expired free trial **requires** an access window (`p_access_until`, max 60 days) from `admin_toggle_restaurant_status` — otherwise the trigger would silently re-block the row. Change all three together or the manual grant breaks in the order path.
- **Password resets are OTP-only — there is no link flow to restore.** `/reset-password` (owner), `/admin/reset-password` (admin) and `/change-password` (031 handover gate) all render `src/components/auth/OtpPasswordReset.tsx`. It calls `resetPasswordForEmail(email)` with **no** `redirectTo`, then `verifyOtp({ email, token, type: "recovery" })` and `updateUser({ password, data: { temp_password: false } })`. Consequences: the Supabase **Reset Password** email template must contain `{{ .Token }}` and not `{{ .ConfirmationURL }}` (copy lives in `docs/email-templates/reset-password.html`), no route reads a recovery session out of the URL hash any more, and `AuthContext` no longer exposes `resetPassword` — if you ever reintroduce `redirectTo`, you must also reintroduce a page that handles the recovery session, otherwise the mailed link dead-ends.
- **Admin SELECT RLS policies** for `restaurants` and `orders` are added in `setup.sql` hardening section (section 8 of the reconciled file). If running migrations individually, run `CREATE POLICY "Admins can view all restaurants" ON restaurants FOR SELECT TO authenticated USING (is_admin())` and `CREATE POLICY "Admins can view all orders" ON orders FOR SELECT TO authenticated USING (is_admin())` separately.

- **`restaurants` has no client write path (034) — and the owner's profile is the one exception, through the RPC.** `update_my_restaurant` is SECURITY DEFINER, verifies ownership via `get_my_restaurant_id()`, and validates every field (name ≤ 80, 10-digit mobile `^[6-9]\d{9}$`, email format, city ≤ 60, address ≤ 300, type whitelisted against `APP_CONFIG.restaurantTypes`, `logo_url` must be `https://`). It maps `''` → NULL so "remove logo" can never store an empty string that renders `<img src="">`, and turns a duplicate `restaurants.email` (`restaurants_email_key`) into the sentence *"That email is already registered to another restaurant."* **`slug` is deliberately not a parameter** — every printed QR standee encodes `/menu/<slug>`, so changing it silently breaks print. `guard_restaurant_columns` is role-gated (`current_user IN ('authenticated','anon')`) rather than value-frozen like `guard_order_columns`, because admin RPCs and `enforce_trial_expiry` legitimately change status/plan/trial dates as the table owner; it allows exactly one client-reachable change — the `status='blocked' / is_active=false / block_reason='Trial expired' / blocked_by='system'` stamp — so it does not depend on BEFORE-trigger firing order. The owner UI ([RestaurantProfileCard.tsx](src/pages/restaurant/components/RestaurantProfileCard.tsx)) mirrors those validations for instant feedback; the RPC stays the authority.
- **The guest menu refreshes by polling a version token (046) — do not "restore" the realtime channel.** `subscribeToMenuForCustomer` opened a `postgres_changes` channel on `menu_items`; a guest is `anon`, which holds no privilege on that table and no policy grants one, so the channel joined, held a socket open and **silently delivered nothing** — an owner could mark an item out of stock and the guest read a dish that was no longer there. The replacement is a plain fetch plus `usePollWhenVisible`: `get_menu_version` every 60 s (35 bytes) and the full menu only when the token moves. Both tempting "fixes" are wrong: re-adding the channel recreates the bug, and granting `anon` SELECT on `menu_items` to make the channel work exposes every restaurant's menu and pricing to every anonymous visitor over PostgREST. ⚠️ Menu staleness is **not** a data-integrity risk — `customer_create_order` re-validates price and availability server-side — so the poll is allowed to be lazy: keep it visible-only and keep the token cheap.
- **The customer pages keep an in-memory snapshot — NOT `persistentStorage`.** Tapping Orders unmounts the menu page, and both pages used to start from nothing on the way back: a full-screen skeleton while everything was re-fetched, and — on the menu — the guest's **cart thrown away with it** (measured: back-navigation took `1 item selected` to `0 items selected`). Each page now keeps its last state in a module-level `Map` keyed by slug (`historySnapshots` in [CustomerOrderHistory.tsx](src/pages/customer/CustomerOrderHistory.tsx), `menuSnapshots` in [CustomerMenu.tsx](src/pages/customer/CustomerMenu.tsx)), seeded into the `useState` initialisers so the returning paint is immediate and a quiet refresh runs underneath. Measured on the production build: Back → dishes on screen in **7–8 ms** with no network, cart intact, and the warm return asks only `get_menu_version` (36 B); the whole menu comes back only when that token moved (verified both ways — unchanged token = no download, changed token = full refetch). ⚠️ Deliberately in memory, not `persistentStorage`: that helper mirrors every value into a **cookie**, and a menu plus a cart is kilobytes against a ~4 KB per-cookie limit, so the save would fail silently on some browsers. Losing it on a reload is the intended lifetime — the server re-validates everything anyway. ⚠️ Two guards keep the menu snapshot honest: it is written only for a row whose `slug` matches the URL, and only once `menuVersionRef` holds a token, so a half-loaded visit can never file restaurant A's dishes — or an empty menu with no skeleton — under restaurant B. Related: the menu loaders read the restaurant id from a **ref** (`restaurantIdRef`), not from `restaurant` state, so their identities are stable; while they depended on `restaurant?.id` the effects re-ran the moment the row arrived, which is how ONE visit ended up asking for the menu twice.
- **Logo upload for owners already exists — do not build a second uploader.** The pipeline is `ImageUpload` → `uploadImageToCloudinary()` ([imageService.ts](src/services/imageService.ts)) → the deployed `cloudinary-sign` edge function (owner/admin-gated, `restaurant_menus` folder), and it now serves menu item images, the restaurant logo and the menu banner. The CDN width it asks for depends on the `ImageUpload` variant — 800 for the square frames, **1600 for the banner** — because the customer banner is drawn 1000 px+ wide on desktop and a `w_800` source goes visibly soft there; `uploadImageToCloudinary(file, maxWidth)` takes the cap, `c_limit` never upscales. `get_restaurant_by_slug` returns `logo_url` and `banner_url`, so a saved logo or banner shows on the customer menu with no other change.

- **A restaurant's slug is permanent and printed — never regenerate it, and never let a client choose it (047).** Every QR standee encodes `/menu/<slug>`, which is why 034 froze the column and why it is not a parameter of `update_my_restaurant`. 047 added the part that was missing: the **database** now refuses an empty or malformed slug (`restaurants_slug_format`), and `admin_create_restaurant` normalises whatever the browser sends, substitutes `r-<6 hex>` when a name normalises to nothing, and claims a unique value with an `ON CONFLICT` retry loop. ⚠️ Do not "improve" this by adding an OUT column to the RPC: that forces DROP + CREATE, which discards the ACL and lets `ALTER DEFAULT PRIVILEGES` hand EXECUTE to `anon`. ⚠️ Do not try to make the database transliterate Devanagari/Telugu/Tamil — PostgreSQL cannot (`unaccent` is European-only and STABLE; ICU collations do not transliterate) and `slugify`'s charmap has no Indic entry. The readable Roman form is the admin's job in the create form; `r-<hex>` is the safety net that keeps the link working.
- **`orders` has no client write path (033).** Status changes go through `transition_order_status` — SECURITY DEFINER, verifies ownership, enforces the state machine and stamps the matching timeline column. `guard_order_columns` then raises on any change to `total` / `subtotal` / `tax` / `discount` / `items` / `restaurant_id` / `order_number` / `created_at` / `customer_name` / `customer_phone` / `customer_notes` / `payment_method` / `payment_status` / `payment_transaction_id`, so tampering fails even for a superuser. Consequences: a client-side `orders.update()` now dies with `42501`, any new payment or status column belongs in the RPC body, and the trigger is the layer that survives a re-run of the blanket `GRANT ... ON ALL TABLES ... TO authenticated` in `setup.sql` section 2 — if that grant is ever re-added, re-apply 033 afterwards.
- **Do not turn the table code back into a number, and do not add a per-table order cap because "the table is verified now".** Two things look tempting after 045 and both are wrong. (1) The code is still a **bearer token**: a photo of the standee can be shared, so it stops invention, enumeration and garbage values, and it makes a leak revocable **per table** (`owner_rotate_table_code` — the reason a random code beats an HMAC, whose secret is all-or-nothing), but it does not prove the guest is sitting there. Physical presence needs L2/L3 in [docs/plans/2026-10-16-order-abuse-defense-plan.md](docs/plans/2026-10-16-order-abuse-defense-plan.md). (2) A per-table cap is still a bad idea for the 043 reasons: the table is **shared** by every guest at it (a 12-guest party on separate phones is normal), and one leaked code would let an attacker spend a real table's quota. The phone cap (10/hour) remains the only refusal in the public order path; 045 added a *validation* (a code that does not resolve) and nothing that caps volume.
- **The public order gate is Turnstile + `submit-order`, and it is OFF until you set a site key.** See [Public order gate](#public-order-gate--turnstile--the-submit-order-edge-function). Three things not to get wrong: the secret lives in Supabase secrets and **never** in the bundle; a Cloudflare **outage fails open** (logged) while a definite `success: false` fails closed — do not "fix" the outage path into a refusal, that is what would take ordering down with a third party; and the browser can still call `customer_create_order` directly until the `revoke execute … from anon` step is run, so **deploying the function alone is not protection**.
- **The restaurant-wide order burst is ALERT-ONLY (042) — do not turn it back into a refusal without reading that migration.** `customer_create_order` still counts orders per restaurant over a rolling 5 minutes, but crossing `c_burst_alert_per_5min` (30) only raises a WARNING and writes one deduplicated `notifications` row (`type = 'order_burst'`); **the guest's order always goes through**. It was made alert-only because (a) 30/5min is not safely above real peaks — Chipotle's highest-throughput units are reported at ~29 transactions per 5 min — and (b) being the only whole-restaurant cap, 30 cheap orders from an attacker were enough to have *every genuine guest* refused while the window stayed full. **The only rate-limit refusal left in the public order path is the PHONE cap (10/hour); the table cap was removed by 043.** (044 later added a *validation* refusal — a table outside the owner's declared `table_count` — which caps nothing and is fail-open while that column is NULL.) An earlier version of this note claimed the phone and table caps were both "per-identity, so they only ever block the caller who caused them" — that was **wrong for the table**. `table_number` is a *shared* identity (every guest at that table) **and is client-supplied**: the table QR only carries `?table=N`, and on the Master QR a guest types it by hand (`Your Table Number` in [CheckoutContent.tsx](src/pages/customer/components/CheckoutContent.tsx)), so 8 cheap orders can lock a **real** table for an hour. A large party ordering on separate phones can also reach 8 legitimately — each device keeps its own cart and no login is involved. And a script simply varies the table, so the cap barely touches a script while it *can* refuse real guests. That is why 043 **dropped** it rather than retuning it; if a table limit is ever wanted again, the fix is a signed per-table token (L1) plus per-session scoring (L3), not a number. The trade-off is deliberate and documented: a script that varies **both** phone and table is no longer stopped at all — the alert is a tripwire, and the real replacement is invisible bot friction (Turnstile/PoW, L2 in [docs/plans/2026-10-16-order-abuse-defense-plan.md](docs/plans/2026-10-16-order-abuse-defense-plan.md)). `notifications` had **no writer before this migration** (0 rows ever) and had **no reader in the UI** until **[049](#) gave it one** (`admin_get_order_burst_alerts()` + a card on the admin dashboard) — before that the alert was visible only in the Postgres log and as a row, which is why 049 exists.
- **A table QR is a capability now (045), and that changed what `table_count` (044) costs when it is unset.** `restaurant_tables` holds one row per table with a random `code`; `/menu/<slug>?t=<code>` is resolved **by the server**, which reads the label out of the database — no client ever names a table. `restaurants.table_count` is still the owner's declaration, but it is now the *input* to `sync_restaurant_tables` rather than a range check: it creates `1..N` rows with fresh codes and **deactivates** (never deletes) the rows above N, so lowering the count and raising it again revives the *same* codes and an already-printed standee resumes working. ⚠️ **NULL = no tables = no dine-in.** That is a deliberate fail-**closed** decision (Master QR is takeaway-only), not the fail-open behaviour 044 had; the honest cost is that a restaurant that never sets the number cannot take dine-in orders at all until it does. ⚠️ 044's range check is **gone**, and that is a strengthening, not a loss: resolving a per-table code proves *which* table instead of trusting a number. `guard_restaurant_columns` still freezes `table_count` for client roles. ⚠️ `orders.table_number` holds the **label** ("5") the server resolved — never a code, never a client value. ⚠️ **Adding `p_table_count` required DROPping `update_my_restaurant` first** — every parameter after `p_name` has a default, so `CREATE OR REPLACE` with an extra argument creates an *overload* rather than replacing the function (035's trap). DROP also discards the ACL, and this database auto-grants EXECUTE on new functions to `anon` via `ALTER DEFAULT PRIVILEGES`, so any future change to that RPC must re-issue `REVOKE … FROM anon, PUBLIC` and `GRANT … TO authenticated, service_role` in the same migration and verify with `has_function_privilege`.
